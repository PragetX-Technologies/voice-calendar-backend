# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000   # run dev server
ngrok http 8000                              # expose for ElevenLabs webhooks during dev
```

No test suite, linter, or build step configured in this repo.

## Architecture

FastAPI backend bridging two ElevenLabs voice agents — Aura (booking) and Echo (reminders) — to a single business's calendar (Apple iCloud via CalDAV, or Google Calendar), plus a single-owner dashboard (login, calendar connect, profile). Single hardcoded owner account (see MongoDB section) — no multi-tenancy, no signup. Two calendar accounts per business: "user" (the caller's own calendar, credentials hardcoded in `.env`) and "provider" (the signed-in business owner's calendar, connected via the dashboard). Writes mirror to both — see `_mirror_to_provider` in each calendar service.

### Request directions

1. **Outbound trigger** (`app/routers/calls.py`, `POST /calls/trigger`) — this backend calls ElevenLabs' API to place a call, passing `customer_name`/`reason`/`phone_number`/`provider` as dynamic variables the agent's prompt can reference. `purpose` ("booking" or "reminder") picks which of the two agents places the call — Aura (booking) still has one agent/phone-number id per calendar provider (`ELEVENLABS_GOOGLE_AGENT_ID`/`ELEVENLABS_APPLE_AGENT_ID` in `.env`, picked by the request's `provider` field, falling back to `CALENDAR_PROVIDER`); Echo (reminder) is a single agent/phone-number id (`ELEVENLABS_REMINDER_AGENT_ID`/`_PHONE_NUMBER_ID`) regardless of provider — only one reminder number exists.
2. **Inbound tool webhooks** (`app/routers/tools.py`, `POST /tools/*`) — ElevenLabs calls back into this backend mid-conversation when the agent decides to list/create/update/delete a calendar event, or fetch business working hours (`get-business-hours`, for availability checks). Every route is gated by `verify_webhook_secret` (`X-Webhook-Secret` header vs `TOOL_WEBHOOK_SECRET`) — the only auth here, since this path has no signed-in session. No `business_account_id` context either; every handler resolves the real provider via `_resolve_provider()` → `calendar_connections_service.get_any_platform()`, which looks up the one connection actually saved for `OWNER_ACCOUNT_ID` — this overrides whatever `provider` value the LLM sent (the LLM regularly gets this wrong, e.g. saying "google" when only "apple" is connected). `business_service.get_any_profile()` similarly always resolves to `OWNER_ACCOUNT_ID`'s profile — do not reintroduce "whichever business has this connected" first-match lookups; that previously returned stale data left over from before the account was hardcoded. `create`/`update`/`delete-event` each fire background SMS/email confirmations to both the customer (`phone_number`/`email` from the call) and the business owner (`business_profiles.mobile`/`.email`, via `_owner_contact`) — same message mirrored to both. `get-business-hours` also returns `now` (ISO datetime, `settings.default_timezone`) and `today` (`"Mon"`..`"Sun"`, matching `hours` dict keys) computed server-side — the prompts tell the agent to read the current date/day from here rather than calculating it itself (LLM date math is unreliable).
3. **Dashboard API** (`app/routers/auth.py`, `business.py`, `oauth.py`, `calendar_view.py`) — JWT-bearer-scoped endpoints for the frontend. Every route depends on `require_account_id` (`app/auth.py`), which just decodes the JWT `sub` claim — always `OWNER_ACCOUNT_ID` in practice, since only one account exists.
4. **Reminder call sweep** (`app/reminder_job.py`, `run_reminder_sweep`) — `BackgroundScheduler` job wired via `lifespan` in `main.py`, runs every 15 min. Queries `calendar_events` for upcoming appointments (next 24h, `reminder_sent != True`), triggers a call per match in-process via `trigger_call(purpose="reminder")` (same function `POST /calls/trigger` uses), then marks `reminder_sent: true`. No retry/backoff on failed calls. To test without waiting on a due appointment: `python -c "import logging; logging.basicConfig(level=logging.INFO); import app.reminder_job as rj; rj.REMINDER_LOOKAHEAD_HOURS = 24*7; rj.run_reminder_sweep()"` (logging must be configured manually outside `app.main`).

### Calendar layer

`app/calendar_service.py` dispatches to whichever backend is active (`settings.calendar_provider`) for the ElevenLabs tool-webhook path only (no `business_account_id`, no `account` param — always "user"). `app/routers/calendar_view.py` (dashboard path) calls `caldav_service`/`google_calendar_service` directly instead, since it needs `account`/`business_account_id` threaded through. Both backends expose the same four functions (`list_events`/`create_event`/`update_event`/`delete_event`), each taking `account` ("user"/"provider") and `business_account_id`:

- `app/caldav_service.py` — Apple iCloud via CalDAV. Per-account client/calendar cache (`_clients`/`_calendars`, keyed by `_client_cache_key`). "user" auth is an app-specific password from `.env`; "provider" auth comes from `calendar_connections_service`. `update_event`/`delete_event` look up the target event via `_find_event_by_uid` — a wide `date_search` (1yr past/2yr future) with manual UID matching, not `calendar.event_by_uid()`, since iCloud's CalDAV server 412s on UID-only queries with no time-range.
- `app/google_calendar_service.py` — Google Calendar API v3, same account/provider split. "user" auth is a long-lived refresh token in `.env` (`scripts/google_oauth_setup.py` mints one interactively); "provider" auth comes from `calendar_connections_service`. `uid` for Google events is the Google event id (client-assigned via `uuid.uuid4().hex` at create, so both accounts' mirrored events share the same id).

Every tool webhook schema has an optional `provider` field (`"apple"`/`"google"`), but `app/routers/tools.py`'s `_resolve_provider()` overrides it from the DB connection anyway (see request-directions #2) — the field is effectively vestigial now that there's only one business account, kept for forward compatibility if multi-tenancy comes back. `POST /calls/trigger` still sets a `provider` dynamic variable at call start (same mechanism as `phone_number`) as a `dynamic_variable`-type tool param in the ElevenLabs dashboard config, not `llm_prompt` — the earlier `llm_prompt` version let the LLM guess and drift between providers mid-call. All datetimes without explicit tz info are assumed to be `settings.default_timezone` (each service has its own `_parse_dt`).

### MongoDB (`app/db.py`, `get_db()`)

Module-level `MongoClient` singleton (`MONGODB_URI`/`MONGODB_DB_NAME` in `.env`), same lazy-cache pattern as the CalDAV client. Collections, one service module each:

- No `accounts` collection — single hardcoded owner account (`accounts_service.py`, `OWNER_ACCOUNT_ID = "owner"`), checked against `OWNER_USERNAME`/`OWNER_PASSWORD` in `.env`. No signup.
- `business_profiles` (`business_service.py`) — business profile (contact/hours/job types), keyed by account id, always `OWNER_ACCOUNT_ID` here. `hours` (`business_schemas.DayHours` per weekday, `"Mon"`..`"Sun"`) drives availability checks: agent calls `get-business-hours` before offering/confirming a slot, no backend-side enforcement (prompt-trust only, plus the `now`/`today` fields — see request-directions #2). `get_any_profile()` is the webhook-path lookup, pinned directly to `OWNER_ACCOUNT_ID`.
- `calendar_connections` (`calendar_connections_service.py`) — per-(account, platform) "provider" calendar credentials (refresh token / app-specific password), kept separate from `business_profiles` so secrets never round-trip through the profile GET/PUT. Stored plaintext (`# ponytail:` note to encrypt later). `get_any_connection()`/`get_any_platform()` are also pinned to `OWNER_ACCOUNT_ID` — don't revert to a bare `find_one({"platform": ...})` first-match query, that can return a stale doc left over from before the account was hardcoded.
- `calendar_events` (`calendar_events_service.py`) — a synced *read cache* of every calendar event, mirrored on every create/update/delete from both `tools.py` and `calendar_view.py` (`$set`-based `upsert_event`, `delete_event`), now storing `phone_number`/`email`/`reminder_sent` too. The live calendar (CalDAV/Google) stays source of truth; `app/reminder_job.py`'s sweep reads this cache to find appointments due a reminder call. `sync_range()` backfills a date range from the live calendar for events that predate this cache — not wired to any endpoint, call manually when needed. Events created before the `phone_number`/`email`/`reminder_sent` fields existed lack them (no backfill migration run).

`app/config.py` defines `Settings` (pydantic-settings), loaded from `.env` — all credentials, JWT secret, Mongo URI, etc. `app/schemas.py` holds tool-webhook + call-trigger request models; `app/business_schemas.py` and `app/auth_schemas.py` hold their respective routers' models.

All routers log every request payload and, on failure, the full exception traceback (`logging.basicConfig` set up in `main.py`) — check the uvicorn console when a live agent call fails, since ElevenLabs only ever hears the agent's generic "having trouble" fallback line.

### SMS / email

`app/sms_service.py` and `app/email_service.py` each append a fixed `PRIVACY_NOTE` to every message in `_send()` (one place, not per-caller). Both take an optional recipient override (`to_number`/`email`); `email_service._send` no-ops if none given — the caller's email is no longer collected by the agent, it's hardcoded via `settings.user_email` (`USER_EMAIL` in `.env`) and passed explicitly from `app/routers/tools.py`. Phone numbers are normalized to E.164 via `sms_service._to_e164()` (uses `settings.default_sms_country_code`, `"+91"`) — also imported into `app/routers/calls.py` so outbound-call `to_number` gets the same treatment, not just SMS.
